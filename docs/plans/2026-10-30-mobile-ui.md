# PixelVault mobile UI implementation plan

> Execute natively, one task at a time. No subagents. Status: proposed; no mobile scaffold or dependency installation has been performed.

**Goal:** Build a distinct phone interface for PixelVault members with shared accounts and APIs, a lightweight browser development loop and a later Android package.

**Architecture:** Add `apps/mobile` to the existing npm workspaces. Share canonical UI, tokens, brand assets, generated contracts and a small transport boundary; keep phone composition separate from the web application. Release the same-origin browser/PWA experience before native authentication and device work are proven.

**Tech Stack:** Existing React/TypeScript, Vite, Tailwind, Shadcn, React Router and TanStack Query; proposed Capacitor for Android and `vite-plugin-pwa`/Workbox for narrowly scoped public-shell caching. Pin compatible versions at execution, rather than adding a second UI/state framework.

**Spec:** [Mobile UI and developer documentation](../specs/2026-10-30-mobile-ui-and-api-docs-design.md). Dependency: [API documentation plan](2026-10-30-api-documentation.md) tasks 1–3 for initial screens; task 4 before financial/meeting flows are declared complete.

## Global constraints

- One repository, backend and member identity. Borrowing/lending is a context inside Home, not a second account or app.
- Proposed primary navigation: Home, Explore, Activity, Inbox, Profile. No desktop sidebar or Community/My dashboard switch in the phone shell.
- Retain PixelVault blue/keyhole branding, Manrope, semantic light/navy tokens and existing illustration/avatar/badge families.
- Use canonical Shadcn controls and Tailwind utilities. No feature-specific CSS and no import of desktop `apps/web/src/styles.css`.
- Minimum 44px touch targets and 16px form inputs. Respect safe areas, keyboard, enlarged text and reduced motion. Exact financial values do not count up.
- PWA caching is public-shell/static-assets only. Never cache private API/document content, queue financial writes or automatically replay uncertain commands.
- Keep live origination/funding disabled. Reputation, proof uploads and a successful checkout return are not proof of creditworthiness or settled money.
- No builds or automated checks under the current visual-only instruction. Automated cases below are deferred release requirements, not permission or passing evidence. Browser/device inspection also needs the applicable user authorization.
- Native compatibility and Android packaging require separately authorized device/build work. No store publication or iOS release is included.

## Review focus

1. Switching accounts or signing out must not retain another member's cached data — task 2's session/cache cases.
2. Offline/timeout/double tap must not duplicate a financial action — tasks 4 and 7's reconciliation cases.
3. Keyboard, large text and system Back must not conceal or accidentally trigger an agreement action — tasks 1, 4 and 8's layout/back cases.
4. Location/device denial, backgrounding or late permission resolution must leave a usable screen and stop capture — tasks 3, 5 and 8's lifecycle cases.
5. A native cookie/upload/event transport must not silently bypass browser security or expose credentials — task 8's compatibility gate.

## Milestones

| Milestone | Working result | Depends on |
| --- | --- | --- |
| M1 | Phone shell with public Explore and reviewed Home/offer concept | Tasks 1–3, initial typed API slice |
| M2 | Authenticated browser member journey: applications, loans, activity, profile and meetings | Tasks 2–6, completed relevant contracts |
| M3 | Installable browser/PWA with bounded public offline shell | Task 7 and permitted verification |
| M4 | Android device proof and packaged internal test app | Task 8, explicit build/device authorization and compatibility evidence |

M1–M3 use the existing backend. M4 is not a condition for useful browser delivery. No milestone creates real loans, accepts agreements or sends money merely to demonstrate the UI.

## File ownership and routes

| Proposed paths | Responsibility |
| --- | --- |
| `apps/mobile/src/app/{router,MobileShell,session}.tsx`, `queryClient.ts` | Routes, shell visibility, member/session boundary and private cache lifecycle |
| `apps/mobile/src/features/<feature>/` | Phone screens, small feature-owned components/hooks |
| `apps/mobile/src/platform/{browser,native}/` | Device/transport adapters; no financial decisions |
| `packages/api-client/src/` | Shared API errors, requests, CSRF and binary download behavior |
| `packages/ui/src/styles/tokens.css`, existing canonical controls | Shared semantic identity and reusable accessible primitives |
| `scripts/mobile-assets.json`, `sync-mobile-assets.mjs` | Explicit selected brand/illustration delivery; original provenance stays intact |
| `docs/surfaces/mobile.md`, `docs/mobile/` | Phone brief, device decisions, release evidence and development instructions |

Browser deployment uses `/m/`; native assets use `/`. Set Vite base and router basename from the target so links do not inherit desktop routes. Child paths are `/`, `/explore`, `/offers/:offerId`, `/activity`, `/applications/:applicationId`, `/loans/:loanId`, `/inbox`, `/inbox/:threadId`, `/meetings/:roomId`, `/profile` and `/members/:handle`; secondary routes cover saved offers, calendar, lender decisions, investments and settings. Full-screen flags are route metadata, not URL substring heuristics.

## Task 2: Share API transport and wire browser identity

**Files:** Create `packages/api-client/package.json`, `src/{index,client,errors}.ts`, `src/client.test.ts`, `apps/mobile/src/app/session.tsx`, `src/app/queryClient.ts`, `src/features/auth/{SignInScreen,RegisterScreen,RecoveryScreen}.tsx`; modify `apps/web/src/app/api.ts` into compatible re-exports/wrappers, workspace aliases and API-client package registration. If the web formatting helpers are reused, extract them unchanged into `packages/ui/src/lib/format.ts`, export them through `packages/ui/src/index.ts` and preserve existing web re-exports.

**Interfaces:** `Transport = (url: string, init: RequestInit) => Promise<Response>`; `createApiClient({baseUrl, transport})` returns `{apiRequest<T>(path, init?), post<T>(path, data), download(path, init?), setCsrfToken(token), clearSession()}`. Re-export the same `ApiError` class to preserve `instanceof`; retain `operationId()` and `items()` web exports. Browser transport uses same-origin credentials; native transport is unimplemented until task 8.

- [ ] Extract existing request/error/CSRF behavior without changing web requests. Keep multipart boundaries intact and separate JSON from binary downloads. Use generated operation types from the documentation work at feature call sites; no client-side financial schema guesses.
- [ ] Wire session bootstrap, sign-in/register, field-error focus, recovery entry and logout confirmation. Rotate the in-memory CSRF token with the session. Do not introduce a token store or claim submitted contact details are verified.
- [ ] Scope private query keys to member identity, clear them on logout/session expiry/account switch, and re-fetch before showing private content after resume. An active request belonging to a former session must not repopulate the new session cache.
- [ ] Record deferred client cases: JSON and multipart, non-JSON download, field/domain/detail errors, missing network, logout clear, CSRF rotation and late response after account switch. Preserve the web API's public surface and request URL/credentials behavior.
- [ ] Commit `refactor(api): share browser transport with mobile`.

**Acceptance:** Existing accounts work in both browser interfaces through the same session endpoints. Sign-out and expiry remove private cached content. No claim of native compatibility is made.

## Task 3: Deliver compact discovery, map and offer planning

**Files:** Expand `apps/mobile/src/features/explore/ExploreScreen.tsx` and `features/offers/OfferScreen.tsx`; create adjacent `explore/OfferCard.tsx`, `SearchSheet.tsx`, `MapScreen.tsx`, `useDiscovery.ts`, `offers/LoanPlanner.tsx`, `CostSheet.tsx` and targeted component-case files. Reuse existing shared art and documented contracts; extract web behavior only where both clients use the same pure logic. Feature paths in the remaining tasks are relative to `apps/mobile/src/`.

**Interfaces:** Discovery uses the existing community/discovery/areas endpoints. `LoanPlanner` calls `GET /api/v1/engagement/offers/{offer_id}/calculator` with its documented query fields; it does not calculate repayment values. Route and query state preserve search, radius, sort and map/list mode when returning from an offer.

- [ ] Implement full-width compact cards, suggestion pills, a merged lender/place input, heart/count, saved action and badges overflow. Roll back failed reactions. Respect pagination and unavailable offers without inventing capacity.
- [ ] Lazy-load Mapbox on explicit map entry. Keep controls in the map, 5/10/50km radius visualization, approximate centers, linked offer selection and an accessible list fallback. Do not request location before the member chooses Near me.
- [ ] Build phone offer detail with lender identity/current terms, amount/frequency/installment controls, estimated summary, expandable cost/schedule and a safe-area Apply action. Keep investor pitch secondary; estimated and signed figures use distinct labels.
- [ ] Record deferred cases for stale place search responses, denied location/WebGL fallback, unavailable offer, failed like rollback, zero results, invalid calculator input and a newer preview superseding an older response.
- [ ] Commit `feat(mobile): add discovery and offer planning`.

**Acceptance:** Members can find, save and inspect an offer with one search and no desktop control stack. Changing a calculator never changes an existing application or agreement.

## Task 4: Build Home, applications and servicing views

**Files:** Expand `features/home/HomeScreen.tsx`; create `features/applications/{ApplicationFlow,ApplicationScreen}.tsx`, `features/loans/{LoanScreen,PaymentSheet,AgreementReview}.tsx`, `features/activity/{ActivityScreen,CalendarScreen}.tsx`, `features/lending/DecisionScreen.tsx`, `features/saved/SavedScreen.tsx` and feature-owned query modules.

**Interfaces:** Consume typed applications/agreements/servicing APIs and `/api/v1/hub/{actions,calendar,decisions,saved-offers}`. Server contracts supply money, dates and eligibility. Existing operation ID/hash/revision rules remain endpoint-specific.

- [ ] Put borrowing/lending context inside Home's main card; show the next obligation, at most four summary tiles, genuine trend data when present and quick links to lender decisions/calendar/saves. Keep fees, collections, future amounts and settlement separate.
- [ ] Add eligibility/request/co-borrower-invitation/review/submit flow. Preserve entered values on validation errors; invitation acceptance and identity verification are separate prerequisites. Do not infer joint liability from a contact entry.
- [ ] Add vertical loan/payment history, schedule, private documents, receipts and full agreement review. Preserve two-party confirmation and explicit signing/funding stages; Back/swipe never submits or accepts. Full analytics and admin operations remain on web.
- [ ] Render payment preview/checkout through current server routes. After a return link, fetch authoritative status; a browser redirect or uploaded receipt does not mark a loan paid. On uncertain response, reconcile the operation before offering a retry; no automatic financial retries.
- [ ] Add date filtering, dates-only ICS, action read state, lender decisions and up-to-three saved comparisons without exposing another member's data. Record deferred cases for centavo/string totals, partial payment, unknown settlement, stale revision/hash, double tap and late/uncertain response.
- [ ] Commit `feat(mobile): add member lending and servicing journey`.

**Acceptance:** An authenticated synthetic member can navigate the complete browser journey with honest states. UI inspection does not require acceptance, disbursement or payment to create convincing screens.

**Interfaces:** Use existing thread APIs and participant-only meetings endpoints. `DevicePreview` owns its stream and cleanup. Full-screen room route metadata hides shell/navigation. Initial update strategy is foreground REST polling with one request at a time, bounded backoff and no hidden-tab polling.

- [ ] Add avatars/unread state and optional coarse online status; preserve scroll/focus on incoming messages. Never expose exact last-seen timestamps where the profile setting is off.
- [ ] Build scheduled waiting room with Manila schedule, Ping/check-in state and readiness guide. Put mic/camera preview controls before the illustration; permission prompts require deliberate actions. Both devices begin off.
- [ ] Compose the full-screen room: conversation and a compact step tray for amount, interest-share projection, documents/terms, mutual acceptance and separate simulated funding/fee confirmation. Reuse existing command/revision rules; show both parties' completion state.
- [ ] Preserve record-only access outside attendance windows; no check-in, upload, capture or financial command is sent by opening records. Release media on leave/background and stop streams from late permission promises.

## Task 7: Add a bounded PWA shell and low-resource workflow

**Files:** Create `apps/mobile/src/sw.ts`, `src/platform/browser/pwa.ts`, `public/manifest.webmanifest`, appropriate brand icons and `docs/mobile/development.md`; modify mobile Vite configuration and the root lockfile. Add `docs/mobile/release-checklist.md`.

**Interfaces:** Browser/PWA build serves `/m/`; service-worker scope is `/m/`. Native mode has no service-worker registration. Prefer `vite-plugin-pwa` injectManifest with an explicit custom worker, following its [official guide](https://vite-pwa-org.netlify.app/guide/inject-manifest).

- [ ] Add a pinned Vite-compatible PWA integration and allowlist only bundled shell scripts/styles, local fonts, icons and selected public illustrations for precaching. Do not create runtime caches for API requests or authenticated pages/files. The static app shell contains no embedded member data.
- [ ] Use an update prompt, not automatic reload during typing, checkout or agreement review. On disconnected/stale state show the status and disable writes; private pages require an online refresh. Logout clears private in-memory cache independently of public shell cache.
- [ ] Document browser-first work with the existing API/workers, `npm run dev:mobile`, physical-device live reload only when needed and separate web/mobile start-stop instructions. Do not run two copies of the backend or install an emulator for everyday styling.
- [ ] Record deferred worker cases for API/cache exclusion, document exclusion, scope isolation from desktop, native registration disabled, interrupted update and no queued writes. PWA output/offline verification needs an explicitly authorized build/inspection; leave release status pending until then.
- [ ] Commit `feat(mobile): add public-shell PWA delivery`.

**Acceptance:** Installation improves access without creating an offline finance database or replay queue. Development remains useful with a single Vite process and the existing backend services.

## Task 8: Prove Android compatibility before packaging

**Files:** Create `apps/mobile/capacitor.config.ts`, `src/platform/native/{transport,lifecycle,links,files}.ts`, later the generated `apps/mobile/android/` project, and `docs/mobile/android-compatibility.md`. Modify API origin settings only if the measured design requires exact trusted origins; preserve browser protections.

**Interfaces:** The native adapter implements task 2's transport contract, including authorized binary/multipart handling. API origin is an explicit HTTPS configuration value, never inferred from a remote link. A native URL handler accepts only allowlisted PixelVault paths and verified checkout-return routes; it never acts on arbitrary commands.

- [ ] After build/device work is explicitly authorized, add compatible pinned Capacitor core/CLI/Android and only the lifecycle/network/system UI plugins actually needed. Use a physical Android device; keep native HTTP/cookie handling behind an adapter. Do not ship a live-reload `server.url`.
- [ ] Run a synthetic native session probe: CSRF bootstrap, sign-in/token rotation, authenticated fetch, process restart, expiry, sign-out, recovery/session revocation and a rejected missing/invalid-CSRF mutation. Inspect actual cookie ownership and origin behavior without printing credentials.
- [ ] Prove multipart photo/evidence upload and authorized download using existing limits, with cancellation and a bounded-memory path. Do not serialize large files through base64 merely to satisfy the bridge. Prove device pickers, camera/microphone denial and cleanup on background/leave; hide unsupported capabilities.
- [ ] Use foreground REST polling for native updates initially. Prove app resume refresh, keyboard/safe area, system Back, approved return links, offline recovery and duplicate/uncertain command handling. A return link re-fetches status and cannot assert settlement. Review foreground WebRTC separately before exposing call actions.
- [ ] Record the device/OS, compatible plugin versions, allowed origins, results and unresolved cases. If the session/privacy guarantees fail, stop native authenticated delivery and retain PWA; write a separate standards-based auth design before changing the login model. Do not weaken CSRF, cookie flags or CORS as a shortcut.
- [ ] With explicit packaging authorization, generate/sync/build a bundled internal Android test app and review it on device. Store credentials/signing keys outside Git; store publication and iOS are separate tasks. Commit `feat(mobile): add verified Android container` only with honest compatibility evidence.

**Acceptance:** An Android package is called functional only after the native session/file/lifecycle gate passes. Visual similarity to the browser app is insufficient evidence.
